# B1: environments, provider intent and composition

This describes the current source API and its validation record, not a
published release. The platform and CLI must use the same compatible major-2
core. [README](../README.md) covers authoring;
[CONTRIBUTING](../CONTRIBUTING.md#the-ir) lists the canonical wire fields.
The [foundation validation record](foundation-validation.md) is historical B0
(major 1) evidence, not B1 release qualification.

## Shared semantic boundary

`blueprint-ir-platform/Config.roc` exposes `Environment`, `Tools`, `Extend`,
`Packages(name, Auto | From(provider))`, named `Overlay` and selected `Overlays`.
Shells and tasks each require `Use(environment)`; tasks additionally require
`Run(argv)`. There is no `In` compatibility adapter, shell-owned tool list or
implicit task environment.

`Lower.lower` checks setting cardinality and invokes the pure
`blueprint-ir-package/Project.roc` validator. Lowering remains a top-level
constant in the platform, so `roc check` forces whole-project validation before
the emitting host runs. Imported modules return ordinary settings; see the
[composition fixture](../examples/composition/Blueprint.roc) and its
[ProjectTasks module](../examples/composition/ProjectTasks.roc).

`Ir.parse` first checks major compatibility, then decodes the canonical model.
The CLI checks required features and calls `Project.validate` again. Pure Nix
rendering also uses the shared validator. Receiving IR is not permission to
bypass semantic checks. Unknown optional fields can be ignored within major 2;
unknown required features and other major versions must fail.

Validation normalizes the omitted `default` source to Auto and resolves one
parent per environment, including forward references. Tools and overlays are
parent-first, then child, deduplicated by first occurrence. Normalized
`parents` lists are empty. Empty or omitted child lists inherit rather than
clear selections. Standalone environments have no implicit overlays.

## Static versus selected-provider checks

- **Whole-project, host-independent:** names, duplicates, source/overlay and
  environment references, inheritance cycles/depth, tool-reference structure,
  nonempty executable argv and NUL rejection. Explicit Nix/Guix sources also
  trigger their native tool grammar checks statically, even in unused
  declarations. Capability checks, unlike grammar checks, follow the request. None of these checks fetch packages or observe installed tools.
- **After backend selection, before staging:** Auto tool grammar and requested
  source/provider compatibility. `Project.check_environment` models `Nix` and
  `Guix` intent; Guix rejects selected overlays. Grammar is deliberately
  conservative: Nix dotted identifiers and Guix package/version/output specs.
- **In Nix:** actual attribute existence and package availability on the target.
  A syntactically valid but missing native name remains in generated output and
  fails in Nix. No translation, alternate-provider retry or package filtering.

Selection belongs to the consumer. The core does not autodetect tools on PATH,
choose a provider based on the host, or execute commands. The reference CLI
explicitly selects Nix. Guix has **pure intent/capability validation only**, not
a renderer, shell executor or task/build implementation.

## Requested closure and rendering

`NixBackend.render_environment(ir, name)` checks and renders the selected
normalized environment, its tools/sources and overlay stack. The reference
CLI uses it for `shell` and `run`. A task needs no shell alias: the renderer
creates a stable `blueprint-env-<environment>` entry. That prefix is reserved
for generated entries, not user shell names.

`NixBackend.render(ir)` selects all environments referenced by shells/tasks;
`gen`, `update`, `check` and `flake` use this full render. An unrelated valid
Guix environment does not block a selected Nix request. It can block a full
render if a shell or task references it. Structural errors, unknown required
features, unsupported declared targets and invalid Nix Raw remain project-wide
errors; closure checking does not permit malformed unused declarations.

Nix imports package sources with the selected environment's ordered overlays.
Declaring an overlay alone never applies it globally. Shell aliases share their
environment's package imports, but `Raw("nix", "shell:<alias>", ...)` belongs
only to that alias, not other aliases or task entries. Unselected package sources
and unselected overlay inputs are omitted. Arbitrary `Input` flake declarations
remain emitted for Raw data; B1 does not analyze their use.

The renderer supports these output shapes: `x86_64-linux`, `aarch64-linux`,
`x86_64-darwin`, `aarch64-darwin`. Other declared Nix targets are errors, not
silently removed entries. Output generation/evaluation does not verify platform
host execution or cross-compilation. Verified execution remains x86_64 Linux.

## Lock and effect boundaries: still B1

The ordinary CLI stages files into `.blueprint/`, copies in `Blueprint.lock`
when present, invokes `nix flake lock`, then copies the resulting lock back.
This happens for `gen`, `shell` and `run`; `update` additionally upgrades inputs.
Switching requested closures can add/remove package inputs and change lock
bytes. Ordinary operations are **not** guaranteed to preserve the authoritative
lock, nor is lock initialization confined to explicit update.

The separate pure library seam
`NixBackend.render_files(ir, target, layout, locked_inputs)` takes caller-owned
absolute paths and already-resolved Nix lock bytes. It checks the requested
target is declared, rejects invalid layout paths and local input/source URLs,
and returns generated flake and lock files without effects. It uses the shared
full renderer, so `target` does not narrow output to one system. Supplied lock
bytes are trusted and copied verbatim, not decoded or validated as a lock
protocol. A caller supplies/resolves them; the renderer does not initialize or
update locks. This seam does not change the reference CLI's lifecycle.

Locked non-flake `Source`, sandboxed artifact `Build`, dependency outputs,
`Workflow`, generic request/plan execution and the stricter explicit-update,
immutable ordinary-lock lifecycle remain B2/B3 work. Local-source rebasing,
relocatable identity and source filtering are not supported by `render_files`.
No B1 documentation or passing renderer test establishes those guarantees.

## Toolchain and release gates

Keep `.roc-version` (`nightly-2026-09-23-c7852fd`) and the basic-cli source pin
`473caa2cc4f3fe9ce4e4682158bb80ebc2e19169`. The source dependency carries required
basic-cli #495 and #498 fixes; it is not an invented compatible release. The Nix
wrapper provisions Roc. A standalone CLI still needs a compatible compiler via
`PATH` or `ROC`: configuration loading compiles/evaluates the app at runtime.
Compile-time checks do not embed the compiler or sandbox configuration imports.

Both bundle gates remain:

```sh
scripts/bundle.sh platform
scripts/bundle.sh platform "$(< blueprint-ir-platform/ir-release)"
```

The first bundles the local core/platform together and runs shared validation,
including module composition. The second must keep testing the committed
released IR. That pin still points to `ir-0.2.0` (major 1), incompatible with
B1's schema and shared `Project` export; an expected blocking failure is not a
passing release gate. Do not silently skip it, substitute a local artifact or
invent a compatible release URL. Only an actual compatible release can unblock
release qualification. A tested local-core snapshot can be handed off as
source-only, explicitly **not release-qualified**.
