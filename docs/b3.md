# B3: ordered workflows and the execution contract

B3 implementation based on B2 `b8e2a40`. Compiler/dependency pins,
repository `flake.lock` and the runtime compiler provisioning are unchanged.
This is source-only, **not release-qualified**: the unchanged major-1
`ir-release` still fails its required bundle gate. B4 handoff remains pending.

## Authoring and wire data

```roc
Workflow("ci", [
    RunTask("check", ["--verbose"]),
    BuildArtifact("app"),
    RunWorkflow("verify"),
]),
Workflow("verify", [RunTask("smoke", [])]),
```

These settings refer to existing declarations, not CLI command strings.
`WorkflowName` checks workflow identities; task and artifact references retain
`TaskName` and `InputName`. `RunTask` appends literal extra argv, preserving empty
strings, quotes, newlines and `--`. No shell parsing, parallelism or scheduler.
Repeated explicit steps repeat, including through shared nested workflows.
Empty workflows are valid no-ops.

IR **2.2** adds optional top-level `workflows: List({name, steps})`. Steps are
`RunTask(Str, List(Str))`, `BuildArtifact(Str)` or `RunWorkflow(Str)`. Populated
workflow declarations require the `workflows` feature, including named empty
workflows. Earlier major-2 records without the field still decode. Unknown
required features, unknown step tags and other majors fail explicitly.
`Ir.parse` decodes; `Project.validate` performs semantic validation. Lowering
still calls that validator at top level so local and bundled `roc check` reject
invalid configurations, not merely runtime execution.

Whole-project validation checks duplicates, unresolved references, cycles and
limits even in unused workflows. Limits are 1,024 workflow declarations, 8,192
declared steps, 128 nesting levels, 4,096 expanded atomic steps per workflow,
and 1 MiB of expanded task argv bytes (configured plus extras). Individual argv
limits remain 4,096 elements / 1 MiB, with a nonempty executable and no NUL.
Build graph/argv limits from [B2](b2.md) remain in force.

Graph validation memoizes subtree count, height and task argv size, rejecting
oversized productive graphs before allocating expansion. Empty subgraphs are
pruned from expansion, so a 128-level doubling empty diamond does not traverse
exponentially many paths. Productive expansion preserves repetitions and visits
at most output-size × depth edges. Nix workflow preparation shares immutable
recipes for identical requests. This is **not** artifact caching: each sequence
entry still performs its own runtime operations and command.

The workflow rendering allowance is **16,777,216 bytes inclusive**, summed once
per distinct atomic request (task name plus exact extras, or build name). It
counts UTF-8 bytes of the complete generated `flake.nix` and every command argv
string, without separators or terminating NULs. All rendered systems, selected
build dependencies, environment definitions, input declarations, Raw and fixed
flake scaffolding count. Shared runner/derived-lock files, plan metadata and
operations do not count toward this text allowance. Repeated identical requests
consume no additional allowance; differing task extras are distinct requests.

Preparation passes the remaining allowance into the same renderer used by
standalone requests. It charges argv first, then emitted chunks before retaining
or joining them: individual input/environment/build definitions, shell entries,
Raw attributes and scaffolding. No dependency-closure or system-sized combined
string is constructed before checking its pieces. An exact-fit request succeeds;
the next byte rejects the entire workflow before effects. Empty expansion checks
its validation-only flake against the allowance but returns no steps. Standalone
requests, inspection and update use the same renderer without this workflow cap.
This bounds retained distinct rendered text, **not total process memory**: input
IR/normalization, an individual definition or Raw value's temporary rendering,
and the final join still allocate. Distinct requests still incur ordinary
validation/rendering work; this is not a performance claim for arbitrarily large
projects.

## Actual importable API

The core package exports `Ir`, `Project`, `Request`, `Plan`, `Layout`, `Sexpr`
and `Value`. The backend package exports `NixBackend`, `Locks` and inspection
metadata `Backend`. The configuration platform additionally exposes
`WorkflowName` alongside `Config`, `EnvName`, `FlakeRef`, `InputName`, `System`,
`TaskName`, `Tool` and `Val`.

- `Config.Setting` adds `Workflow(WorkflowName, List(Config.WorkflowStep))`.
- `Ir` adds `Workflow`, `WorkflowStep` and `AtomicStep` types above.
- `Project.workflow_steps(ir, name) -> Try(List(Ir.AtomicStep), Str)` validates
  the whole project and returns only ordered `RunTask` / `BuildArtifact` values.
- `Request` is `Generate | Shell(Str) | Run(Str, List(Str)) | Build(Str) |
  Workflow(Str)`.
- `NixBackend.preflight(ir, request, target, layout) -> Try({}, Str)` checks
  selection, capabilities and layout before the caller reads authority.
- `NixBackend.plan(ir, request, target, layout, locks) -> Try(Plan, Str)` derives
  the **entire sequence**, including lock identity/translation, before effects.
  Standalone requests and workflows share atomic selection and rendering.
- `Plan` is now `{ steps: List(Plan.Step) }`, replacing B2's single-step record.
  Each step contains `action: Generate | Shell(Str) | Run(Str) | Build(Str)`,
  `files`, `argv`, `artifacts` and `operations`. A standalone request has one
  step; an empty workflow has none. There is no compatibility execution path.
- `Plan.File`, `Plan.Artifact` and `Plan.Operation` retain their B2 fields.
  Artifacts describe unique dependency-first builds **within that step**;
  dependencies can appear again in later explicit builds. Operations remain
  `VerifyLocal({path, nar_hash})` and `Snapshot({root, destination, exclude})`.
- `Locks.decode`, `from_nix`, `encode`, `derive`, `NixBackend.update_files`,
  `local_checks`, `render` and `render_environment` retain their B2 roles.

Callers provide target, layout and decoded authority, with no host discovery or
backend selection in the core. Plans are data derived by compiled-in backend
code; no file/process recipes are deserialized from configuration. Nix rendering
and lock internals remain in the separate backend package. The independent
[consumer](../fixtures/consumer/main.roc) uses the sequence API directly without
calling Blueprint or maintaining a second renderer.

## Consumer-owned execution

`blueprint workflow NAME` uses the generic name argument parser, with help and
explicit unknown-workflow diagnostics. The CLI loads IR once and obtains the
complete plan before entering its shared executor. It does not reload config or
replan individual steps while executing a workflow.

For each step, the executor:

1. Performs its operations in order, failing immediately on any error.
2. Stages its generated files, never authority.
3. Invokes its exact argv from the project root and reports task/build failure.

This means later unsupported task environments or transitive build requirements,
invalid layouts and mismatching supplied locks reject the complete request
before an earlier task can write a marker. Filesystem observations, native
package resolution and command failures remain runtime errors: preflight is not
an assertion that future mutable files or package attributes will succeed.
Failure leaves already completed effects in place; there is no rollback,
provider fallback or retry. Consumers own confirmation policy; the reference
CLI adds no interactive confirmation.

Every explicit build repeats local-pin verification and snapshots current
working-tree files, including untracked/task-generated files. Its entire build
dependency graph uses that operation's snapshot. The executor does not retain
resolved artifacts by name between steps. Unchanged sources may naturally share
Nix outputs. An intervening task that changes a locked source causes later
verification to fail with an explicit-update diagnostic, even if a previous
artifact exists in the store. Tasks after such edits also encounter verification.

B2 filtering, separate read-only source/dependency views, output containment,
local Linux isolation witness and filesystem policies are unchanged. Ordinary
workflows preserve authoritative lock bytes, inode, mode and mtime; only explicit
`update` publishes authority. Runtime helpers/compiler remain provisioned by the
Nix package. Serialize shared-workspace use and avoid concurrent source mutation;
this is not a transaction against external writers. Tasks and compilation are
not sandboxed. Only local x86_64 Linux execution is verified; Guix execution,
remote builders, non-Linux execution and B4 qualification remain outside scope.
