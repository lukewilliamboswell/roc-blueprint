= Run blueprint

Run these in the directory containing `Blueprint.roc`, or set `BLUEPRINT_ROOT`.

[cols="3,5",options="header"]
|===
| Command
| Meaning

| `blueprint` / `blueprint gen`
| Generate `.blueprint/` from existing matching authoritative pins

| `blueprint shell [NAME]`
| Generate the selected alias's environment, then enter it (default alias `default`)

| `blueprint run TASK [-- ARGS...]`
| Generate the task's environment, then run its argv with extra arguments

| `blueprint build NAME`
| Snapshot and build an artifact plus dependencies; print its actual store path

| `blueprint workflow NAME`
| Execute an ordered task/build workflow, stopping on failure

| `blueprint tasks`
| List tasks and their environments

| `blueprint update`
| Explicitly initialize/update and atomically publish the authoritative lock: the pins of package sources, inputs and build sources, and the digest of every fetched program on every declared system

| `blueprint update NAME...`
| Update only the named package sources, inputs, build sources and fetched programs, keeping everything else of a lock that is current for `Blueprint.roc`. Local `path:` inputs are read again either way. A named program is downloaded again whether or not its URLs changed

| `blueprint requirements [--json] [TASK...]`
| Say what the named tasks need, or every task: a provider, fetched programs, tools of the machine. See <<what-tasks-need>>

| `blueprint check`
| Run the compiler check and validate all shell/task/build environments without requiring a lock

| `blueprint spec` / `blueprint flake`
| Print the Spec or the generated flake

| `blueprint --help`
| Project help; subcommand help lists tasks, aliases and builds
|===

== What each command validates

Provider capability checks follow the requested environment closure; unrelated
valid provider declarations do not block selected operations. Whole-project
structural validation and required-feature checks still apply. Full rendering
(`gen`, `update`, `check`, `flake`) checks all shell/task/build environments.

== The lock and generated files

* *Commit* `Blueprint.roc` and the authority (default `Blueprint.lock`, a
  versioned S-expression listing each pinned source and its digest);
  generated state (default `.blueprint/`) is not committed: `blueprint`
  writes a `.gitignore` there that ignores everything in it. A lock written
  by an older `blueprint` is refused; run `blueprint update`.
* Normal `gen`, `shell`, `run`, `build` and `workflow` require matching pins and never
  rewrite authority or independently update derived locks.
* `nix develop` takes the bash it runs a shell or task with from a flake input
  named `nixpkgs`, so the generated flake gives that name to the first Nix
  package source declared and that bash is pinned by `Blueprint.lock` like
  every tool, unless the project declares an input named `nixpkgs` itself.

== What tasks need

`blueprint requirements` reads `Blueprint.roc` and nothing else: not `PATH`,
not the store and not `Blueprint.lock`. It answers before anything is
installed or resolved, and gives the same answer on every machine. The system
is `BLUEPRINT_TARGET`, or the one it runs on.

[source]
----
$ blueprint requirements
system x86_64-linux
providers: nix
task check [dev]: programs roc-stable; expects gh, git; roc packages 2
task host [zig]: provider nix (nix#zigpkgs."0.16.0"); programs roc-stable; expects gh, git; roc packages 2
----

With `--json` the report is one JSON object for a program to read:

[source,json]
----
{"format":1,"system":"x86_64-linux","providers":["nix"],"expects":["gh","git"],"tasks":[
 {"name":"check","environment":"dev","providers":[],"tools":[],"programs":["roc-stable"],"unavailable":[],"expects":["gh","git"],"roc_packages":2},
 {"name":"host","environment":"zig","providers":["nix"],"tools":["nix#zigpkgs.\"0.16.0\""],"programs":["roc-stable"],"unavailable":[],"expects":["gh","git"],"roc_packages":2}]}
----

[cols="1,4",options="header"]
|===
| Field
| Meaning

| `format`
| The number of this shape, `1`. Every field below is always present. A change a reader of format 1 could misread gets another number.

| `system`
| The system the report is for.

| `providers`
| The providers that must be on the machine to run the reported tasks on that system, each once. `"nix"` is there exactly when one of those tasks has, in its environment on that system, a tool from a Nix package source. A Nix source that is declared and that no reported task uses does not put it there. Neither does a shell, a build or `blueprint update`: they are not tasks, a build always needs Nix, and an update needs it whenever the project declares something Nix resolves.

| `expects`
| The programs those tasks expect the machine to have already, each once.

| `tasks`
| One object for each task, in the order asked, or in the order of `Blueprint.roc` when none is named.

| `tasks[].providers`, `tasks[].tools`
| The providers that task needs, by the same rule, and the tools they supply, as `Blueprint.roc` writes them.

| `tasks[].programs`, `tasks[].unavailable`
| The programs its environment fetches on that system, and those it lists that do not exist there. A task with an unavailable program cannot run on that system.

| `tasks[].expects`, `tasks[].roc_packages`
| The programs the task expects of the machine, and how many Roc packages its environment has.
|===

A task that is not declared is an error, and nothing is printed for the
others. To install Nix only where it is needed, test whether `providers`
holds `"nix"` for the tasks a job runs:

[source,sh]
----
blueprint requirements --json check | jq -e '.providers | index("nix")'
----

== What update needs and records

`blueprint update` starts Nix only when `Blueprint.roc` declares something Nix
resolves: a Nix package source, an input or overlay, or a build source,
including the bundle of a Roc package that a build uses. It looks for `nix`
before doing anything else and says why it needs it. A project that declares
none of these is updated with no Nix on the machine, and so is a named update
of fetched programs alone in any project.

For each fetched program and each declared system, the lock holds the URLs the
program is declared with, the SHA-256 and the length of the download, and how
the digest was obtained:

[cols="1,4",options="header"]
|===
| `obtained`
| Meaning

| `Computed`
| `blueprint update` downloaded the bytes and hashed them. Nothing else was to be had.

| `Published`
| The release that serves the download reports this digest, and the bytes were not downloaded. A run on that system checks its download against it.

| `Both`
| It hashed the bytes, and the release reports the same digest and length.
|===

An entry whose URLs are unchanged is kept, and nothing is asked or downloaded
for it. Otherwise the download for the system the update runs on is fetched
and hashed, and is kept in the store for the run that follows. A program that
is the very download `blueprint` fetched as its own compiler, as a
`Recipes.roc_nightly` of that nightly is, is hashed from the store and not
fetched a second time. When the first
URL is a GitHub release asset,
`https://github.com/<owner>/<repo>/releases/download/<tag>/<asset>`, the
release is asked once what it publishes. A digest computed here that differs
from the published one stops the update, and nothing is written. For another
system the published digest is recorded and nothing is downloaded; an asset
with no published digest, or a URL that is not a release asset, is downloaded
and hashed instead.

The question to GitHub carries no token, and GitHub answers 60 such requests
an hour from one address. A question that is refused, that cannot be put, or
whose answer does not describe a release does not stop the update:
`blueprint update` says so once for the release, downloads and hashes that
release's assets for every system, and records each as `Computed`. A digest
that is published and differs from the computed one always stops it. A run
never asks GitHub anything.

After writing the lock, `blueprint update` prints every download host the new
lock names and the lock before it did not, one to a line:

[source]
----
Blueprint.lock now names download hosts it did not name before:
  github.com
----

It prints nothing when there is none. A new host in a lock update is worth a
reviewer's look.

== Environment variables

* *`BLUEPRINT_ROOT`* names the directory containing `Blueprint.roc`
  (default: the current directory).
* *`BLUEPRINT_WORKSPACE`*, *`BLUEPRINT_GENERATED_ROOT`*, *`BLUEPRINT_LOCK`*
  choose caller paths; relative values resolve against the selected project
  root, not the invocation directory. Out-of-tree generated roots are supported.
* *`BLUEPRINT_TARGET`* selects a declared target (default: this machine's
  System). *`ROC`* selects the compatible compiler; unset, it is found on
  `PATH` or downloaded into the store.
* *`XDG_CACHE_HOME`* names the directory that holds the store of downloads,
  `blueprint/` (default: `.cache` in `HOME`). No request `blueprint` makes
  carries a token or any other credential.
