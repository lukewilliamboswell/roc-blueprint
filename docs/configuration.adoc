= Write Blueprint.roc

`Blueprint.roc` is a Roc application on the roc-blueprint platform. It
provides `config`, a list of settings:

[source,roc]
----
app [config] { pf: platform "<the platform URL of a release>" }

config = [
	Name("my-project"),
	Packages("nix", From(NixPackages("github:NixOS/nixpkgs/nixos-unstable"))),
	Environment("dev", [Tools(["nix#git"])]),
	Shell("default", [Use("dev")]),
]
----

xref:getting-started.adoc#write-a-first-blueprint-roc[Get started] has a
complete file with the current URL.

== Top-level settings

[cols="3,4",options="header"]
|===
| Setting
| Meaning

| `Name(Str)`
| Project name. Required, once.

| `Systems(List(System))`
| Declared targets, each `<arch>-<os>` of a known architecture (`x86_64`, `aarch64`, `riscv64`, `i686`, `armv7l`, `powerpc64le`) and operating system (`linux`, `darwin`, `windows`, `freebsd`). Defaults to x86_64 and aarch64 on Linux and macOS; an empty list is invalid.

| `Packages(InputName, From(Provider))`
| A package source and the set it is: `NixPackages(FlakeRef)` or `GuixPackages(Str)`. Every source is declared; none is implied.

| `Overlay(InputName, FlakeRef)`
| Named overlay input; only environments selecting its name apply it.

| `Input(InputName, FlakeRef)`
| Other flake input; not a tool source or overlay.

| `Environment(EnvName, List(EnvironmentSetting))`
| Named tools and scoped overlays, optionally inherited.

| `Shell(EnvName, List(ShellSetting))`
| Named alias with exactly one `Use(environment)`. `blueprint shell` selects alias `"default"`.

| `Task(TaskName, List(TaskSetting))`
| Named argv command with exactly one `Use(environment)` and one `Run(argv)`. No shell alias is required.

| `Source(InputName, FlakeRef)`
| Locked non-flake input, e.g. `Source("assets", "path:./assets")`.

| `Build(InputName, List(BuildSetting))`
| Sandboxed artifact with required `Use`, exact argv `Run`, relative `Output`; optional `Inputs` and `Needs`.

| `Workflow(WorkflowName, List(WorkflowStep))`
| Ordered `RunTask(name, extra_argv)`, `BuildArtifact(name)` and `RunWorkflow(name)` steps.

| `Raw(backend, target, Val)`
| Provider-specific data; see <<pass-data-to-the-provider>>.

| `Custom(kind, name, Val)`
| Extension data. The current CLI rejects unsupported extensions.
|===

== Environment settings

Inside an `Environment`, `Tools` and `Overlays` occur at most once, `ToolsFor`
occurs at most once per System, `Command` occurs at most once per command
name, `ToolWith` occurs at most once per tool, and `RocPackages`, `Programs`
and `Expect` occur at most once each:

[cols="3,4",options="header"]
|===
| Setting
| Meaning

| `Tools(List(Tool))`
| Native package names. `"git"` uses source `default`; `"stable#jq"` uses source `stable`. A Nix name is an attribute path; quote a segment that contains dots, as in `"zigpkgs.\"0.16.0\""`.

| `ToolsFor(System, List(Tool))`
| Add tools only for a declared target System. Each System occurs at most once per Environment.

| `Command(Str, Tool)`
| Expose one tool's main program under another command name, without adding the tool's own executables.

| `ToolWith(Tool, List((Str, Val)))`
| A tool built with options its package takes; see <<configure-a-tool>>.

| `RocPackages(List(Str))`
| Released Roc bundle URLs to lock, so Roc programs in the environment resolve them without downloading.

| `Programs(List(Program))`
| The programs the environment has on `PATH` that are downloaded: each is `Fetch(ProgramName, recipe)`, a command name and a function from the System to `File(url)`, `Archive(url, format, member)` or `Unavailable`. `Mirrored(download, urls)` adds alternate URLs for the same bytes to a `File` or an `Archive`. `Recipes.roc_nightly(tag)` and `Recipes.file(template)` are such functions.

| `Expect(List(ProgramName))`
| Programs the machine must already have on `PATH`. They are checked for, never installed, and no version is asked of them.

| `Overlays(List(InputName))`
| Ordered selection of declared overlay names.

| `Extend(EnvName)`
| Inherit one environment's tools, overlays, commands, configured tools, Roc packages, programs and expected tools before appending this environment's selections.
|===

Inheritance deduplicates by first occurrence, parent first. Omitted or empty
`Tools`/`ToolsFor`/`Overlays` lists do not clear inherited values. A standalone environment
has no overlays unless selected. `Run` must contain a nonempty executable;
arguments remain separate strings, including extra CLI arguments after `--`.
There is no `In` setting or implicit task environment. One name is only one
of a program, an expected tool and a `Command` in an environment, including
what it inherits.

A program that several environments list is bound once, as in
`roc_stable = Fetch("roc-stable", Recipes.roc_nightly("nightly-2026-10-04-130536d"))`,
or inherited with `Extend`: one name always means the same downloads. Every
text of a recipe is checked as what it is where it is written. A `System` is
`<arch>-<os>` of an architecture and an operating system Blueprint knows, also
in a `match` pattern and beside `==`; a `Url` is `https://<host>/<path>` with
no credentials, query or fragment; a `Member` is a relative path inside an
archive; a tag is `nightly-YYYY-MM-DD-<commit>`. Give a recipe of more than a
line its type, `System -> Config.Download`, so that a mistake in it is
reported on its own line.

A `System` is not text. To write it into a URL, use
`Recipes.file("https://example.org/1.0/tool-{system}")`, whose template also
takes `{arch}` and `{os}`, or `"https://example.org/1.0/tool-${system.to_str()}"`.
With `${system}` alone the compiler reports a type mismatch of
`from_interpolation` on `Url`, at the first line of the file.

== Choose where tools come from

A tool that a package source installs is written `"<source>#<name>"`, for a
source declared with `Packages` (a fragment inside `config`):

[source,roc]
----
Packages("nix", From(NixPackages("github:NixOS/nixpkgs/nixos-unstable"))),
Packages("stable", From(NixPackages("github:NixOS/nixpkgs/nixos-24.05"))),
Environment("dev", [Tools(["nix#git", "stable#jq"])]),
----

The source is always written, in `Tools`, `ToolsFor`, `Command` and
`ToolWith` alike. No source is implied: `"git"` alone is refused where it is
written, with both ways out, which are to name a declared source or, if the
machine already has the tool, to list it in `Expect`. A tool that names a
source the project does not declare is refused with the sources it does
declare. A project whose environments have no such tool declares no source,
and Nix is not started for it.

An environment that Nix must build although it has no tool of its own, such
as the sandbox of a build whose environment is empty, is built with the first
Nix source declared, in the order of `Blueprint.roc`. The bash `nix develop`
runs comes from that source too.

The core does not autodetect a provider or translate package names. Nix is
asked only for an environment that has a tool from a Nix source. Guix source
intent and pure capability validation exist, but there is *no Guix renderer
or executor*.
An incompatible requested environment fails; it never retries another provider.
Missing native packages and unavailable target packages fail in Nix rather than
being silently filtered out. Unsupported Nix target declarations fail before
file writes or provider execution.

== Add tools for one system

For a shell shared by Linux and macOS, put common tools in `Tools` and declare
platform libraries explicitly:

[source,roc]
----
Environment("dev", [
	Tools(["nix#git", "nix#python3"]),
	ToolsFor("x86_64-linux", ["nix#wayland", "nix#alsa-lib"]),
]),
----

`ToolsFor` is provider-neutral Spec intent. It applies to inherited environments,
shells, tasks and builds on that System; undeclared systems and duplicate
declarations are rejected during evaluation.

== Give a tool another command name

`Command` keeps a pinned tool beside another tool of the same name. For example,
repository scripts can run on one fixed Roc release while the project is built
with whichever `roc` is already on `PATH`:

[source,roc]
----
Overlay("roc", "github:roc-lang/roc-overlay"),
Environment("dev", [
	Overlays(["roc"]),
	Command("roc-stable", "nix#rocpkgs.nightly-2026-09-10-a670e34"),
]),
----

The environment gains `roc-stable` and no `roc`, so a script can start with
`#!/usr/bin/env roc-stable`. The command runs the tool's main program as its
package declares it; a package that declares none fails in Nix. Command names
are plain file names. An extending environment inherits commands and replaces
one by declaring the same name.

[#configure-a-tool]
== Configure a tool

Some packages are built to order. A Rust toolchain from rust-overlay comes
with the host's standard library only; the targets it can compile for and
its extra components are options of the package. `ToolWith` names the tool
and those options:

[source,roc]
----
Overlay("rust", "github:oxalica/rust-overlay"),
Overlay("zig", "github:mitchellh/zig-overlay"),
Environment("host", [
	Overlays(["rust", "zig"]),
	Tools(["nix#zigpkgs.\"0.16.0\""]),
	ToolWith("nix#rust-bin.stable.\"1.95.0\".default", [
		("targets", List([Str("x86_64-unknown-linux-musl"), Str("aarch64-unknown-linux-musl")])),
		("extensions", List([Str("rust-src")])),
	]),
]),
----

The environment gains `cargo` and `rustc` from Rust 1.95.0 with both musl
targets and the standard library's source. Zig needs no options: zig-overlay
names each release as an attribute, which `Tools` selects.

The options are the names and values the package's own `override` takes,
written as `Val` data: strings, integers, booleans, lists and attribute
sets. They are passed as data and are never an expression, so they select
among what the package offers and cannot say how to build it. A package
that takes no options, or not the ones named, fails in Nix.

A tool is either plain or configured in an environment, not both. An
extending environment inherits configured tools; configuring an inherited
tool replaces all of its options. Three things are not supported:

* options on a `ToolsFor` or `Command` tool;
* rust-overlay's `fromRustupToolchainFile`, which reads a file of the
  project: the generated flake does not see the project's files;
* configured tools from a Guix source.

== Pin an exact version of a tool

A tool's version is whatever its source holds at the pinned revision.
`Blueprint.roc` names the tool, not its version, so to hold one tool at an
exact version, give it a package source of its own, pinned to a nixpkgs
revision that ships that version. For CPython 3.14.3:

[source,roc]
----
Packages("py", From(NixPackages("github:NixOS/nixpkgs/<revision>"))),
Environment("dev", [Tools(["nix#git", "py#python314"])]),
----

`<revision>` is a full nixpkgs commit whose `python314` is 3.14.3. To find
one, look at the history of the package's file in nixpkgs, or evaluate a
candidate:

[source,sh]
----
nix eval --raw github:NixOS/nixpkgs/<revision>#python314.version
----

How the source is written decides whether the version can move:

* A source that names a *revision*, as above, never moves. `blueprint update`
  resolves it to the same commit every time. Change the version by editing
  the revision.
* A source that names a *branch*, such as `github:NixOS/nixpkgs/nixos-25.05`,
  is moved by `blueprint update` and by `blueprint update py`, and takes
  whatever version the branch then has. `blueprint update nix` leaves it
  alone.

Nothing in `Blueprint.roc` states the version, so nothing fails if it changes.
If a version matters, assert it where the tool is used, for example by having
the project's check task run `python3.14 --version` and compare.

An overlay that publishes each version under its own attribute needs no second
source: select the attribute, quoting a segment that contains dots.

[source,roc]
----
Overlay("zig", "github:mitchellh/zig-overlay"),
Environment("dev", [Overlays(["zig"]), Tools(["nix#zigpkgs.\"0.16.0\""])]),
----

[#roc-packages]
== Lock the Roc packages scripts use

A Roc script names its platform and packages by release URL, and Roc downloads
them on first use. `RocPackages` names those bundles for an environment
instead, so Blueprint has them in place before its scripts start, and they
run at all in a sandboxed build, which has no network:

[source,roc]
----
Overlay("roc", "github:roc-lang/roc-overlay"),
Environment("scripts", [
	Overlays(["roc"]),
	Command("roc-stable", "nix#rocpkgs.nightly-2026-10-04-130536d"),
	RocPackages([
		"https://github.com/roc-lang/basic-cli/releases/download/0.24.0/AEjfyaMFFbh8FJrkkHJy68riVNPr3Qp6c6PawWQjBwMH.tar.zst",
		"https://github.com/roc-lang/http/releases/download/1.0.0/6ZUwqYhCS8PU9Mo6MF7oV82ET2o7KYb57CLKDq4cq4sS.tar.zst",
	]),
]),
Task("release", [Use("scripts"), Run(["roc-stable", "scripts/release.roc"])]),
Build("notes", [Use("scripts"), Run(["roc-stable", "scripts/notes.roc"]), Output("notes.txt")]),
----

Each URL must be `https://` and end in `<hash>.tar.zst`. The hash is that of
the bundle's bytes, so the URL itself says what the download must be: for a
shell or a task, Blueprint downloads a missing bundle and has the compiler
unpack it, which fails unless the bytes are those the name is the hash of.
Nothing is recorded in `Blueprint.lock` for that, and no Nix is needed. A
sandboxed build cannot download, so the bundles of an environment a build
runs in are also fetched by Nix: `blueprint update` records those in
`Blueprint.lock` like any other source, and Nix checks the bytes against that
pin. An extending environment inherits its parent's bundles.

*List every bundle, including dependencies of dependencies.* basic-cli above
depends on `http`, so both are listed. `roc deps <file>` prints the URLs a
program depends on. Blueprint does not read package headers, so it cannot add a
missing one for you. A bundle that is not listed is downloaded by Roc as usual
in a shell or task, and fails to resolve in a sandboxed build.

What Blueprint writes, and where:

* *`blueprint shell` and `blueprint run`* publish the environment's bundles
  into Roc's own package cache before entering it: the directory
  `roc/packages` under `$XDG_CACHE_HOME`, or under `~/.cache` when that is
  unset. Each bundle becomes the directory `<hash>` there, the files the
  compiler unpacked from the download, which is where Roc looks before
  downloading. A `<hash>` directory that
  already has a `main.roc` is never touched, whether Roc downloaded it or an
  earlier run published it; one without a `main.roc` is incomplete and is
  replaced, as Roc itself would. The copy is made in a temporary directory
  beside it, named `blueprint-<hash>.<random>.tmp`, and renamed into place, so
  another Roc process never sees half a package. Nothing else is written, and
  nothing is downloaded or written when every bundle is already there or the
  environment has no Roc packages. If the cache is deleted, the next run
  downloads and publishes again.
* *`blueprint build`* does not use that cache. The build gets a package cache
  of its own inside its build directory, holding only its environment's
  bundles, and `XDG_CACHE_HOME` points the build's command at it.

A build sees only the tools its environment declares, so a build that runs Roc
needs a Roc tool, such as the `roc-stable` command above.

== Compose settings from modules

Use ordinary Roc lists and functions for composition, not a plugin registry.
https://github.com/lukewilliamboswell/roc-blueprint/blob/main/examples/composition/ProjectTasks.roc[ProjectTasks.roc] returns
`List(Config.Setting)`; its https://github.com/lukewilliamboswell/roc-blueprint/blob/main/examples/composition/Blueprint.roc[app]
concatenates those settings into `config`. Imports do not install tools or add
runtime operations to the CLI.

== Pass data to the provider

The Nix provider accepts attribute data at two targets:

[source,roc]
----
Raw("nix", "shell:default", Attrs([
	("shellHook", Str("echo ready")),
	("RUST_LOG", Str("debug")),
])),
Raw("nix", "flake", Attrs([("formatter", Str("nixpkgs-fmt"))])),
----

* `shell:<alias>` adds attributes to that alias's `mkShell` call, not other
  aliases or tasks using the same environment.
* `flake` adds attributes to flake outputs.

Values are `Str`, `Int`, `Bool`, `List([...])` and `Attrs([(name, value), ...])`.
They are data, not Nix expressions. Duplicate attributes and overrides of
managed `packages`/`devShells` are rejected. Raw for other providers is ignored.
