= Understand the architecture

Blueprint gives repository-owned commands declared environments and, when
requested, a managed artifact-production contract. This chapter defines its
responsibilities for contributors, provider authors and downstream consumers.

[[goals]]
== Goals and non-goals

Many tools turn a description of an environment into a working one for a
single ecosystem, and tie the project's intent to that ecosystem's formats and
commands. Blueprint separates the two. Shared contracts state intent,
dependency authority and execution evidence; every ecosystem-specific concern
belongs to a replaceable provider.

**The protocol is the product; providers are adapters.**

The protocol is the Spec, the Lock, the provider contract and the versioned
reports and records. A provider implements part of it for one ecosystem.

=== Goals

* Realise the same Blueprint through different package ecosystems, or through
  Blueprint's own store, on Linux, macOS and Windows. This is a long-term
  goal; <<provider-neutrality>> says what ships today. Core-managed
  downloads, Roc packages, expected host tools and tasks already work
  without any ecosystem, including on Windows.
* Pin dependencies in a reviewed Lock that only explicit resolution changes,
  and verify pinned content before use.
* Give an artifact an explicit build contract: declared files, inputs,
  dependencies, executor and output, with capabilities checked before
  effects.
* Explain what a build consumed and what changed, from typed evidence rather
  than from reports reconstructed after the fact.
* Keep planning pure, so that another host can import the core types and
  perform the effects itself.

=== Non-goals

* Owning compilation, packaging, validation or release logic. The
  repository's scripts keep it.
* Discovering dependencies hidden in arbitrary commands. A build declares
  what it consumes.
* Translating package names between ecosystems, or choosing a provider
  automatically.
* A second artifact cache. Providers own caching and substitution.
* Sandboxing tasks or the evaluation of `Blueprint.roc`. Only a managed-build
  executor enforces isolation, and only the guarantees it advertises.
* Pinning or versioning tools the machine already has. An expected tool is
  looked for by name.
* Arbitrary composition of providers within one request.
* Running workflow steps in parallel.

[[purpose]]
== What Blueprint owns

A project keeps compilation, packaging and validation logic in its own scripts.
Blueprint describes how to run them: tools, pinned inputs, selected project
files, dependencies, outputs and ordered workflows. It does not discover
arbitrary script dependencies or decide a project's release policy.

[cols="1,4",options="header"]
|===
| Owner | Responsibility
| Repository | Commands, compilation and packaging logic, validation and release policy.
| Configuration | Explicit environments, tasks, builds, inputs, outputs and workflow order.
| Pure core library | Types, semantic validation, dependency relationships, request planning and evidence comparison.
| CLI or another host | Filesystem, network and process effects described by constrained plans.
| Provider | Native resolution, recipe preparation, execution and cache behavior for supported capabilities.
| Release automation | Reviewing and admitting published artifacts, publication and advisory decisions.
|===

A Task is a common runner around a command. A Build adds an explicit contract
for producing an artifact from declared inputs. Both may invoke the same script;
Blueprint does not take ownership of the script's algorithm. A Workflow orders
these operations rather than inferring their dependencies from script contents.

[[provider-neutrality]]
=== Provider neutrality is an enduring constraint

Shared contracts define capabilities and guarantees independently of native
formats. Provider adapters own package grammar, native recipes, process
arguments, store paths and metadata. Another executor need not imitate Nix or
provide every capability. Unsupported capabilities fail before effects rather
than silently weakening isolation or a reproducibility check.

Source resolution, environment tools and build execution are separate roles.
Sources name their resolver; builds select a named executor. Registering an
unselected provider must not change the request. Unsupported combinations are
rejected explicitly; neutrality does not promise arbitrary mixed-provider
composition or portable ecosystem-specific package names.

Nix is the shipped complete package resolver and managed-build executor.
Core-managed verified downloads, Roc packages, expected host tools and tasks
also work without Nix. Independent adapter fixtures test shared boundaries;
they are not a second production provider. Guix source intent is not evidence
of a working Guix executor.

Providers own their native caches and substitution. Blueprint supplies the
selected inputs and interprets typed results; it does not implement a second
artifact cache or infer a cache hit from a successful command.

[[terms]]
== Terms

[[terms-data]]
=== Configuration and data

[cols="1,4",options="header"]
|===
| Term | Definition
| Blueprint | The authored `Blueprint.roc` configuration.
| Spec | Its normalized, validated, versioned description of intent.
| Source | A declared external content origin, with explicit resolver ownership.
| Component | A requested package within a source's native package universe.
| Execution system | The operating system, architecture and platform on which an operation executes.
| Artifact target | The platform an artifact is intended to run on. It may differ from the execution system; scripts currently own cross-compilation settings.
| Lock | Committed dependency authority: exact pins, declared resolution intent and recorded verification evidence.
| Artifact | A produced or fetched file/tree. Its role must be stated; a location alone does not identify its content.
| Store | Disposable local materialization of pinned or produced content.
| Host facts | Explicitly observed machine requirements that Blueprint does not supply or pin.
| Environment | Selected tools, fetched programs, variables and expected host requirements for execution.
| Task | Exact command argv executed in an environment, with repository-owned behavior and side effects.
| Build | An artifact-producing command with declared files, inputs, dependencies, executor and output.
| Workflow | An ordered sequence of tasks, builds and nested workflows.
| Activation | Structured search-path and environment-variable operations for entering an environment.
| Input snapshot | Captured selected project files and their executable bits, together with the selected pinned inputs and build settings.
| Request plan | Validated operations, dependency relationships, capabilities and permitted preparation effects.
| Prepared build | Captured inputs and the exact provider-native recipe with its build identity, ready for execution.
| Build result | Prepared build identity, output locations and execution evidence established by the provider.
| Report | A rendering of typed inspection or execution evidence, with a defined input and compatibility boundary.
|===

`Systems` and `BLUEPRINT_TARGET` retain their established names, but select the
execution system in this contract. They do not introduce an artifact-target
framework or prove that cross-compiled output runs on its intended target.

=== Identities, digests and locations

[cols="1,4",options="header"]
|===
| Term | Comparison domain
| `content_identity` | Pinned input content, compared together with its provider. Opaque to consumers outside that provider's contract.
| `build_identity` | A fully prepared executable build, compared together with its provider. Includes the provider's selected inputs and recipe semantics. A changed build identity means the request changed, not that output bytes differ.
| File digest | Exact original file bytes under a named hashing scheme; an archive's hash includes compression and archive metadata.
| Tree digest | Directory content under a named tree-hashing scheme. A Nix NAR hash and an archive SHA-256 are different measurements.
| Output digest | Measured content of a produced artifact under a named scheme.
| `path` | A location of content; it is not automatically a content checksum.
|===

Equal content identities do not imply equal builds: commands, selected files,
tools and options also matter. Equal build identities do not prove
deterministic execution. A checked rebuild provides evidence about repeated
execution; it does not prove determinism for every execution.

For Nix, the build identity is its derivation path, and the returned output
store path is a location. Consumers must not interpret opaque provider
identities or compare them across providers.

[[terms-stages]]
=== Stages

[cols="1,3,3",options="header"]
|===
| Stage | Input | Responsibility
| Evaluate | Blueprint | Produce and validate the Spec without effects.
| Resolve | Spec, previous Lock and source responses | Explicitly select dependency pins and record verification evidence.
| Fetch | Lock | Obtain and verify the pinned bytes without changing authority.
| Realise | Pinned inputs and declared environment | Materialize tools and activation data.
| Plan | Spec, Lock, request and execution system | Validate relationships and capability requirements before effects.
| Prepare | Validated build request and selected project files | Capture inputs and obtain the exact native build recipe/identity.
| Execute | Prepared build or task plan | Run through the selected host/provider and validate results.
| Activate | Realized environment | Describe environment operations as data.
| Present | Typed data | Render human output, JSON or shell syntax for a consumer.
| Inspect | Explicitly supplied authority or evidence | Derive a read-only explanation without discovering hidden dependencies.
|===

Preparation may fetch pinned content and write caches. It does not resolve new
pins or start the requested build or dependency builds. A provider must refuse
preparation that requires unsupported evaluation effects. Execution uses the
captured inputs and native recipe, rather than silently reevaluating a changed
working tree.

[[terms-roles]]
=== Pure planning and effect execution

The core library and provider adapters return data and constrained steps. They
perform no I/O. The CLI is one effect host; another application may import the
same core types and execute authorized operations itself. Calling both the
library and its host "Core" obscures this boundary.

Executable steps are distinct from inspectable evidence. Parsing a saved
record must never authorize executing it. Human output and JSON are renderings
of the same typed result, rather than independently reconstructed models or
raw provider stdout.

[[layers]]
== Authority, execution and release evidence

The Lock is dependency authority, not a complete build description. A build
also consumes its command, selected project files, tool options and declared
dependency builds. Captured inputs can include untracked or task-generated
files; the Lock alone cannot reconstruct them.

Local successful-build evidence records what was prepared and obtained. It is
disposable operational state, not a replacement lock. A failed build, planning
or explanation must not replace the successful baseline. Missing or
incompatible evidence means unavailable, never unchanged.

An SBOM describes selected artifact composition. Neither a lock projection nor
an SBOM is implicitly a complete executable build graph. Release admission is
a separate repository policy: obtaining a cached result does not authorize
adopting newly published bytes.

For example, a native-input producer can compare the exact current build
identity in Linux admission CI, then publish reviewed evidence bound to the
selected declaration/file snapshot and artifact digest. Consumers on other
systems verify that evidence and the artifact bytes without preparing a Nix
build. Relevant local edits make the admission stale. A producer must not embed
its own final build identity in its recipe inputs; final result evidence belongs
outside the artifact's production inputs.

[[stage-responsibilities]]
=== Build and workflow execution

A request first validates structure and capabilities before effects. A workflow
then executes in order and stops on failure. Each build captures its inputs when
reached, after earlier tasks may have changed files. Repeated explicit build
steps prepare again; the provider may reuse identical results through its cache.
Blueprint must not reuse a result by build name across intervening tasks.

Selected files and dependency identities allow changes to flow through the
declared graph. Explanations distinguish changed declarations, changed build
identities and measured output changes. A script reading undeclared ambient
inputs cannot receive guarantees beyond the executor's enforced contract.

[[commands-as-flows]]
=== Commands use the same model

Tasks use the common runner. Builds, preparation and explanations use the same
request and prepared-build objects. JSON is optional presentation, not the
architecture's integration mechanism. Saved local evidence supports local
explanation; arbitrary historical record comparison remains separate work.

[[invariants]]
== Invariants

[[inv-1]]
=== Invariant 1: Shared capabilities are provider neutral

Native details stay scoped to their provider. Explicit source ownership and
executor selection determine routing without ambient provider selection.

[[inv-2]]
=== Invariant 2: Only explicit resolution changes dependency pins

Ordinary planning, preparation and execution preserve the Lock. They still
consume declared commands, settings, selected files and host requirements.

[[inv-3]]
=== Invariant 3: Authority and evidence have different responsibilities

Pins and their verification decisions belong in the reviewed Lock. Captured
build inputs, results and measured outputs are execution evidence. Neither
silently expands or rewrites the other's authority.

[[inv-4]]
=== Invariant 4: Pinned content is verified before use

Fetched bytes are checked against their declared authority. Native build
caches use the provider's established integrity contract.

[[inv-5]]
=== Invariant 5: Materialization is disposable

A cache may be deleted without losing committed dependency authority. Rebuilding
also requires the matching configuration and captured project inputs; the Lock
alone is insufficient for arbitrary local builds.

[[inv-6]]
=== Invariant 6: Guarantees state their host dependence

Expected tools are checked, not pinned. Tasks and configuration evaluation are
not sandboxed. Isolation and reproducibility claims must name the capability
actually enforced by an executor.

[[inv-7]]
=== Invariant 7: Planning is pure and effects are constrained

Providers return typed plans. Hosts execute only granted operations. Unsupported
capabilities and invalid selected relationships fail before effects.

[[inv-8]]
=== Invariant 8: Rendering happens at the edge

Activation remains data. Shell presenters own escaping. Machine and human
presentations share typed results; native process output is decoded first.

[[inv-9]]
=== Invariant 9: Inspection declares its evidence boundary

Lock inspection reads committed authority without a Store or project evaluation.
Build explanation can compare declared/captured execution evidence. Missing
coverage is explicit; inspectors must not invent a complete graph from reports.

[[inv-10]]
=== Invariant 10: Formats have explicit compatibility contracts

Spec, Lock, build records and public reports version their own semantics.
S-expressions serve the authority and local records; JSON is useful optional
presentation. A package version, wire format and compiler version are distinct.
Blueprint 0.7.0 consumes current Spec 3 and Lock 2 contracts. Earlier authority
is unsupported; adoption uses explicit reviewed resolution, not runtime
conversion.

[[invariant-changes]]
=== What changed in 0.7 and why

Two invariants changed in 0.7. Both changes are deliberate.

Invariant 2 used to say that only Resolve makes choices, and that every later
stage is a pure function of the Lock, the System and the host facts. Managed
builds made that untrue: a build also consumes its command, selected project
files and settings, none of which the Lock holds. The invariant now states
what still holds: only explicit resolution changes pins.

Invariant 9 used to say that inspectors read only committed data, and that a
Report needing anything else meant the Lock was incomplete. `explain build`
compares the current request with the last successful local build record,
which is disposable evidence that does not belong in the Lock. The invariant
now lets an inspector read such evidence when it declares what it read and
reports missing evidence as unavailable. Lock inspection still reads only the
committed Lock.

[[coupling-test]]
== The coupling test

An ecosystem implementing an existing capability should need an adapter, not a
new shared meaning. A consumer should use typed plans/results and their
renderings, not reconstruct dependencies from unrelated JSON reports. New
capabilities may require versioned semantics or constrained host effects.

Review a change by asking whether repository logic remains in scripts, source
ownership is explicit, execution guarantees are accurate, identity comparisons
are well-defined and a provider can implement the capability without Nix-shaped
native data. A second provider fixture is useful evidence of those boundaries;
it does not establish production support or arbitrary provider composition.
