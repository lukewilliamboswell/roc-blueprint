[.lead]
roc-blueprint gives everyone who works on a project, and its CI, the same
tools at the same versions. A project describes its tools, the commands that
use them, its builds and its workflows in one typed file, `Blueprint.roc`,
and commits a reviewed `Blueprint.lock` that pins exactly what was chosen.
The `blueprint` command carries both out on Linux and macOS, runs tasks on
Windows, and starts Nix only for what a project takes from Nix.

.How to use this manual
****
New to Blueprint, or deciding whether to use it:: Start with
<<what-blueprint-is>>. It explains the idea in plain words, and
<<the-words-this-manual-uses>> defines the terms the later chapters use.
Using it for the first time:: Follow <<get-started>>.
Writing a configuration:: <<write-blueprint-roc>> describes every setting, and
<<build-artifacts-and-run-workflows>> the sandboxed builds.
Looking up a command or variable:: See <<run-blueprint>>.
Reading an inspection report in pure Roc:: See <<consume-lock-inspection-in-roc>>.
Describing release composition:: See <<artifact-bound-software-bills-of-materials>>.
Running a project where no package provider is installed:: Read <<work-without-a-provider>>.
Looking for a project to adapt:: Browse <<learn-from-the-examples>>.
Writing a provider or judging a design change:: Read
<<understand-the-architecture>> and <<the-spec-the-lock-and-providers>>.
Changing roc-blueprint itself:: Read <<contribute>>.
Releasing or looking after the repository:: Read <<maintain-and-release>>.
Upgrading:: See <<release-notes>>.
****
