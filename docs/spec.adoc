= The Spec, the Lock and providers

This chapter is for someone reading or producing a Spec, writing a provider,
or changing how `blueprint` plans its work.
xref:architecture.adoc#terms[The architecture chapter] defines the terms.

== What the Spec holds

`roc Blueprint.roc` prints the Spec as an S-expression: records are
`((field value) ...)`, lists `(a b)`, tags `Tag` or `(Tag payload ...)`, and
`;` starts a comment. `blueprint-core/Spec.roc` documents every field.

In outline:

* `format` — `((major 3) (minor 0))`; see <<compatibility-of-the-formats>>.
* `name`, `systems` (strings such as `"x86_64-linux"`).
* `sources` — package sources with explicit versioned provider declarations
  `{ name, version, ref }`. Every source a tool names is declared; validation
  inserts no package source. Checked authoring shorthands such as
  `From(NixPackages(...))` produce these declarations.
* `resolvers` — `{ provider, inputs }`, explicit provider ownership of
  non-package source and input names. The platform writes the Nix entries for
  `Input`, `Overlay`, `Source` and Roc bundle sources itself; validation
  refuses an input with no owner or with two.
* `executors` — `{ name, provider, source }`: a named executor, its provider
  and its bootstrap package source, empty for an executor that needs none.
* `build_executors` — explicit executor selection for each Build.
* `inputs` — `{ name, url }`: inputs a resolver fetches. An environment that
  lists one in `overlays` applies it to its package set as that provider
  defines; the Spec records no provider-specific kind.
* `environments` — `{ name, parents, tools, overlays }`; tools are
  `{ source, name }`, where `source` is a declared source, and overlays are
  ordered input names. Validation resolves a
  single parent, deduplicates parent-first selections and clears `parents`.
* `system_tools` — optional `{ environment, system, tools }` selections. They
  inherit parent first and only enter the environment on their named System.
* `commands` — optional `{ environment, name, tool }` launchers. Validation
  flattens inheritance; a child replaces a same-named inherited command.
* `configured_tools` — optional `{ environment, tool, options }`: a tool and
  the options its package is built with, an `Attrs` value. Validation
  flattens inheritance; a child replaces an inherited tool's options, and a
  tool an environment also has plain is rejected.
* `roc_packages` — optional `{ environment, name, source }`: a Roc bundle's
  content hash and the `build_sources` entry that names its URL. The platform
  derives both from the bundle URL (`roc-<hash>`, `tarball+<url>`);
  environments sharing a bundle share one source. Validation flattens
  inheritance, parent first. The Core fetches the bundles of a task or a
  shell itself. A provider resolves and locks such a source only when a
  build's environment has the package (`Project.resolved_build_sources`), so
  Roc packages that tasks and shells alone use need no provider.
* `programs` — optional `{ name, system, urls, unpack, path }`: a program
  downloaded for one System, under the command name `name`. `urls` is a
  nonempty list, the primary first and then alternates for the same bytes,
  each once. `unpack` is `File`, `TarGz`, `TarXz` or `Zip`; `path` is the program inside
  the unpacked archive and empty for a `File`. A program with no entry for a
  System is unavailable there. The Lock records the digest; the Spec never
  does.
* `environment_programs` — optional `{ environment, programs }`: the declared
  programs an environment has on `PATH`, by name.
* `expects` — optional `{ environment, programs }`: programs the machine must
  already have on `PATH`. They are checked for, never installed. Validation
  flattens the inheritance of both, parent first and each name once, and
  rejects a name an environment has from two of a program, an expected tool
  and a command.
* `shells` — `{ name, environment }` aliases.
* `tasks` — `{ name, environment, run }`, with nonempty executable argv.
* `build_sources` — `{ name, ref }`, locked non-flake sources, separate from
  package-provider `sources`.
* `build_files` — optional `{ build, paths }` selections. Omission keeps a whole-project snapshot; an explicit empty list selects no project files. Requires `build-files`.
* `builds` — `{ name, environment, inputs, needs, run, output }`; named source
  and build references, exact argv and contained relative file/directory output.
* `workflows` — `{ name, steps }`; typed `RunTask(Str, List(Str))`,
  `BuildArtifact(Str)` or `RunWorkflow(Str)` steps, with ordered bounded expansion.
* `raw` — `{ backend, target, value }`, passed through to one provider (the
  wire field keeps the name `backend`).
* `extensions` — `{ kind, name, value }`, blocks a provider may understand.
* `requires` — features the config uses beyond the core (`"raw"`,
  `"extensions"`, `"sources"`, `"builds"`, `"build-files"`, `"workflows"`, `"system-tools"`, `"commands"`, `"roc-packages"`, `"configured-tools"`, `"programs"`, `"expects"`), so an older `blueprint` can say what's missing.
  Required features are independent of the Spec major; unsupported required
  capabilities are rejected before effects.

`Value` is `Str`, `Int`, `Bool`, `List` or `Attrs`. Its S-expression encoder
and parser are hand-written to avoid recursive-codec derivation problems.
`requires` is reserved in Roc; the Roc field is `requires_`, and `Sexpr` drops
a trailing `_` on the wire. There is no major-1 shell `packages` field.

`Lower.lower` checks authoring-setting cardinality, asks the recipe of each
`Fetch` in an environment's `Programs` once for every declared System and
keeps its answers as `programs` (the function never reaches the Spec; a
program listed by several environments is there once, and two recipes under
one name that answer differently for the declared Systems are refused), then
calls `Project.validate` as a top-level constant. The CLI calls that same semantic validator after
`Spec.parse` and required-feature checks, so external Spec does not bypass reference
or graph rules. `Spec.parse` rejects other majors before decoding nested records;
parsing alone does not establish semantic validity.

Static checks cover generic references, duplicates, inheritance cycles, argv,
download URLs (`+https://<host>/<path>+` with no credentials, query or
fragment; `+http://127.0.0.1+` is accepted so that a test can serve one)
and each source's own grammar for the names of its tools. A tool that names
no declared source is refused with the sources that are declared. Package
existence and target availability are Nix runtime checks. Core validation never
probes the host or installs/fetches anything.

== What the Lock holds

`Blueprint.lock` is versioned S-expression dependency authority. Its `intent`
records resolution declarations, including explicit provider ownership.
Provider-namespaced `hints` preserve checked native authority, such as the Nix
lock graph.

Each `sources` entry is `{ name, provider, ref, rev, digest }`, and `digest` is
`sha256:<hex>`. The Nix adapter converts a remote entry's NAR hash to that
form; a local entry carries Blueprint's own tree digest from core `Tree`; a
`SourceFile` entry has provider `"file"` and the flat SHA-256 of the unchanged
original bytes, not of an unpacked tree. These measure different things. The
public inspection contract exposes `content_identity` separately, with
explicit file, tree or unknown digest kind and inert namespaced metadata.

`fetched` holds one `{ name, system, urls, sha256, size, obtained }` per
declared program and System: the URLs it was declared with, the SHA-256 in hex
and the length of the download, and in `obtained` whether the digest was
`Computed` from the downloaded bytes, `Published` by the release that serves
them, `Both`, or `Unstated`.

Only explicit update changes pins. Ordinary requests validate freshness and
verify selected materialization without rewriting authority. Local sources use
project-relative declarations and checked tree digests rather than checkout
locations. A dirty locked source needs explicit update.

The Lock does not contain arbitrary selected project files, prepared build
recipes, output hashes or successful execution records. These belong to their
own declared evidence types. An SBOM describes artifact composition and is not
a substitute for the build graph.

A lock is read only in the current format. `blueprint update` writes it, and
is the one command that accepts a lock it cannot read, by replacing it. Every
other command refuses such a lock and names that command. Reviewed immutable
source references in the configuration constrain what resolution selects.

== Compatibility of the formats

* The decoder accepts the same `major`, whatever the `minor`; consumers must
  still reject unsupported required features and semantically invalid data.
* *Minor* (compatible): a new optional top-level field (missing fields
  default to empty, unknown ones are ignored), or a new `requires` feature.
* *Major* (breaking): anything else, such as a new required field, a new
  field inside a nested record, or a new `kind` tag.

== What a provider does

The pure core validates declarations and plans requests. Providers are pure
adapters that return constrained operations; the CLI or another host performs
filesystem, network and process effects. Registering a provider grants no
ambient ownership of shared sources.

A source names its resolver. Package sources carry versioned provider intent.
Other sources, inputs and overlays are assigned in `resolvers`: the platform
writes the Nix entries for `Input`, `Overlay`, `Source` and Roc bundle sources,
and an explicit `Resolver(provider, names)` assigns one of them to another
provider instead. Each build selects a named executor with `Execute("native")`.
`Executor("native", Nix("pkgs"))` declares a Nix executor whose bootstrap
package source is `pkgs`; `Adapter(provider, source)` declares another
provider's executor, whose source may be empty. Both write
`{ name, provider, source }`. A build never infers its executor from the first
package source.

Adapters validate their own native package/source grammar through the pure
validation boundary used by both authoring and CLI ingestion. Core validation
owns references, cycles, ownership and shared capabilities. Checked constructors
must not expose unchecked provider JSON as configuration intent.

A provider may implement resolution, environment tools, managed execution or a
subset. Capability checks follow the selected request closure. Unsupported
mixed resolvers or executors fail before effects; general composition and a
second production implementation remain follow-up work.

Shared request plans describe dependencies and preparation requirements.
Prepared builds bind captured files, tools, pins and commands to a native build
identity. Build execution uses that exact preparation; typed results decode
provider output before human or JSON presentation. Providers own native caches
and substitution, not Blueprint's report layer.

`gen`, `shell`, `run`, `build` and `workflow` require existing matching authority. Only
explicit `update` resolves new pins and publishes authority; normal commands
stage derivatives and prohibit native lock updates. Named input declarations
remain stable across selected closures; selected overlays remain scoped and
ordered. Local authority contains relative identity and Blueprint tree digests
(core `Tree`, computed and verified by the CLI without Nix), not checkout
paths. Dirty local inputs fail until explicit update. Local verification, caller
observation and Nix's filtered project copy repeat per explicit build, never reusing artifact results
by name across tasks.

A new feature usually means: a setting in the platform (`Config.roc`,
`Lower.roc`), then either an `extensions` kind or a new optional Spec field
(a minor bump), then support in a provider. Prototyping it as `Raw` or `Custom`
first needs no Spec change at all.

=== The provider contract

`blueprint-core/Provider.roc` defines the contract as one record. The CLI uses
only this record: `scripts/src/StaticChecks.roc` fails if
`blueprint-cli/main.roc` reaches into a provider's own modules.

[cols="2,5",options="header"]
|===
| Field
| Purpose

| `name`
| Short provider name, such as `"nix"`. Spec `raw` entries with this name are for this provider.

| `features`
| The Spec `requires` features the provider implements.

| `build_capabilities`
| The build operations it supports; see xref:builds.adoc#capabilities-and-guarantees[Capabilities and guarantees].

| `build_guarantees`
| What a successful build by it establishes. Neither list is evidence that planning ran or checked a sandbox.

| `realises`
| Whether it supplies the tools of a package source with a given provider intent.

| `validate_source`
| Check a package source declaration against its native grammar.

| `validate_tool`
| Check a tool name against its native grammar.

| `validate_executor`
| Check an executor declaration it owns, such as a required bootstrap source. `blueprint check`, `plan build` and `explain build` without `--prepare`, and request planning call it.

| `validate_reference`
| Check the reference of an input or build source its resolver owns against the provider's grammar. The core requires only readable text.

| `activation_argv`
| The argv that prints what the provider's shell for a step would export, without entering it.

| `activation`
| Decode that output into an `Activation`: search-path directories and exported variables, each marked as the provider's.

| `render`
| The files it would generate for the whole Spec, for inspection.

| `inspect_lock`
| Project committed authority into per-source content identities and namespaced metadata, without a Spec, host or effects.

| `preflight`
| Refuse a request it cannot realise, before any effect.

| `realise`
| The ordered steps for one request, from the validated Spec and Lock. Never resolves or changes pins.

| `build_prepare_argv`
| The argv that prepares a build step's exact native recipe.

| `build_prepared`
| Decode that output into a prepared build: its build identity and outputs.

| `build_execute_argv`
| The argv that executes a prepared build, with options such as a checked rebuild.

| `build_result`
| Decode the execution output into a build result with namespaced metadata.

| `build_inputs`
| The locked inputs one build imports directly.

| `build_sources`
| The lock entries the whole build closure uses, for provenance.

| `build_exclusions`
| Project paths left out of a captured snapshot.

| `build_local_inputs`
| Selected local pins with their paths and digests, for the host to verify.

| `resolve`
| The programs to look for, files to stage and argv to run to produce a native lock, for every input or for named ones.

| `lock_from_native`
| Convert that native lock into a Lock.
|===

Every adapter supplies every field, but only the roles it plays need
meaningful answers. The rest return empty lists, `Ok({})`, or an error that
refuses the request before effects.

* An environment-only adapter supplies the tools of its package sources. It
  implements `name`, `realises`, `validate_source`, `validate_tool`,
  `preflight` and `realise`, and refuses other requests. The test in
  `blueprint-core/Realise.roc` headed "An environment-only adapter owns its
  native grammar" is one, with no build support and no bootstrap source.
* A resolver-only adapter produces pins for what it owns. It implements
  `name`, `resolve`, `lock_from_native` and `inspect_lock`, and
  `validate_source` when it owns package sources.
* An executor adapter runs builds. It implements `build_capabilities`,
  `build_guarantees`, `validate_executor`, `preflight` and `realise` for build
  requests, the four `build_*` preparation and result functions,
  `build_inputs`, `build_sources`, `build_exclusions` and
  `build_local_inputs`.

`blueprint-cli/ProviderContractTest.roc` is an independent fixture that
resolves, enters environments and runs builds through the same record
without any Nix protocol.

=== The Nix adapter

The Nix adapter uses locked package sources, ordered selected overlays and
explicit execution-system tool selections. Managed builds use a versioned
standalone runner, filtered project files, read-only inputs and artifacts, exact
argv and validated outputs. They receive declared tools on `PATH` and package
roots under `BLUEPRINT_TOOLS`; this does not activate `stdenv` setup. Runtime
namespace authorization witnesses stay outside the derivation identity. Local
x86_64 Linux is the verified isolation implementation; remote builders are
disabled for this contract.

Nix preparation disables import-from-derivation and does not execute dependency
builds. Execution and checked rebuild target the exact prepared derivation.
Native details stay namespaced in metadata; the derivation path is the Nix
build identity. See xref:builds.adoc[Build artifacts and run workflows] for
planning, results and local evidence.

The generated flake declares a `nixpkgs` input that follows the first package
source it renders, whatever that source is called, because `nix develop` takes
the bash it runs from the input of that name. A project that declares its own
input named `nixpkgs` gets no alias. The Lock's native graph must carry that
root edge exactly as the declarations determine it; decoding refuses a lock
whose edge differs.

An environment with no tool of its own, such as the sandbox of a build whose
environment is empty, is rendered with the bootstrap source of the Nix
executor the project's builds select, and with the first Nix source declared
when no build selects one. A Nix executor needs a bootstrap source:
`Nix(source)` always names one, and `validate_executor` refuses an empty one
however the Spec was written.
