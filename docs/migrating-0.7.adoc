= Adopt 0.7.0

Blueprint 0.7.0 intentionally changes configuration and public APIs before 1.0.
Upgrade the CLI, platform, imported core/provider packages and report consumers
as a coordinated change. Do not mix the 0.7 platform with an older CLI.

== Make ownership explicit

Package declarations continue to use checked constructors such as
`Packages("pkgs", From(NixPackages(...)))`. Assign non-package sources, inputs
and overlays to their resolver, then declare and select each build's executor:

[source,roc,snippet=unchecked]
----
Packages("pkgs", From(NixPackages("github:NixOS/nixpkgs/nixos-unstable"))),
Source("assets", "path:./assets"),
Resolver("nix", ["assets"]),
Executor("native", "nix", "pkgs"),
Environment("producer", [Tools(["pkgs#bash", "pkgs#coreutils"])]),
Build("assets", [
    Execute("native"),
    Use("producer"),
    Files(["scripts/produce.sh"]),
    Inputs(["assets"]),
    Run(["bash", "scripts/produce.sh"]),
    Output("dist/assets"),
]),
----

The executor no longer follows whichever package source is declared first.
Core-owned `SourceFile` inputs need no external resolver. Every referenced
source and executor must be declared; unsupported combinations fail rather than
guessing an owner. Keep compilation and packaging behavior in your scripts.

== Resolve current authority explicitly

Blueprint 0.7.0 reads the current Lock 2 contract. Earlier lock formats are
unsupported; there is no lock-conversion command or automatic upgrade path.

Update configuration and run `blueprint check`. If the project has an
unsupported lock, retain it in version history for review and remove that file
before running `blueprint update`. Review and commit the newly resolved lock as
an explicit dependency change. The update resolves the adopted configuration;
it does not promise to reproduce an older lock's dependency decisions.

Use reviewed immutable source references in configuration when you want to
constrain what resolution selects. Review the resulting pins and verification
evidence before adopting the new authority.

Generated state is disposable. Clear the project's generated `.blueprint/`
state when adopting 0.7.0. The next successful build establishes a fresh local
explanation baseline.

== Use current report and library contracts

* Lock report format 2 exposes `content_identity` for pinned input content.
  Compare it together with its provider.
* `LockSnapshot.source_content_identity` returns the provider-qualified
  `ContentIdentity` value from the current lock projection.
* Build result schema 2 exposes `build_identity` for the fully prepared native
  build request. Its comparison domain also includes the provider.
* Validate current lock projections with `lock-snapshot-v2.schema.json`.

Use the CLI, platform, imported packages and report consumers from the same
current contract. A content identity, build identity, original-file/tree/output
digest and result path answer different questions; they are not interchangeable.

Spec major 3 defines explicit ownership and executor declarations. Lock and
report formats carry their own versions; they are not determined by package
version 0.7.0. Check the relevant version before consuming data.

== Use the integrated build interface

Use `blueprint plan build NAME` for declared relationships and add `--prepare`
for an exact build identity. Use `blueprint explain build NAME [--prepare]` to
compare against the last successful local build. Both accept `--json`; scripts
need not reconstruct relationships from lock and SBOM reports.

A managed build can reuse a provider result without adopting newly published
release bytes. Downstream release policy remains explicit: compare exact
prepared identities in capable admission CI, bind reviewed evidence to selected
configuration/files and artifact digests, and verify that binding on consuming
machines. Do not claim that a whole-lock checksum describes only the selected
producer inputs, or infer equal output bytes merely from input comparison.
