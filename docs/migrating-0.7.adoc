= Upgrade to 0.7.0

Blueprint 0.7.0 intentionally changes configuration and public APIs before 1.0.
Upgrade the CLI, platform, imported core/provider packages and report consumers
as a coordinated change. Do not mix the 0.7 platform with an older CLI.

== Make ownership explicit

Package declarations continue to use checked constructors such as
`Packages("pkgs", From(NixPackages(...)))`. Assign non-package sources, inputs
and overlays to their resolver, then declare and select each build's executor:

[source,roc,snippet=unchecked]
----
Packages("pkgs", From(NixPackages("github:NixOS/nixpkgs/nixos-unstable"))),
Source("assets", "path:./assets"),
Resolver("nix", ["assets"]),
Executor("native", "nix", "pkgs"),
Environment("producer", [Tools(["pkgs#bash", "pkgs#coreutils"])]),
Build("assets", [
    Execute("native"),
    Use("producer"),
    Files(["scripts/produce.sh"]),
    Inputs(["assets"]),
    Run(["bash", "scripts/produce.sh"]),
    Output("dist/assets"),
]),
----

The executor no longer follows whichever package source is declared first.
Core-owned `SourceFile` inputs need no external resolver. Every referenced
source and executor must be declared; unsupported combinations fail rather than
selecting a fallback. Keep compilation and packaging behavior in your scripts.

== Preserve existing dependency decisions

After updating configuration, run `blueprint check`, then
`blueprint lock migrate`. Review and commit the migrated authority. Migration
preserves recorded pins and verification evidence and performs no fetching or
resolution. An ambiguous ownership mapping fails; correct the declarations
rather than using migration to select new dependencies. Use explicit
`blueprint update` when you intend to change dependency pins.

Generated state is disposable. Remove incompatible local build records if
necessary; this loses only the previous explanation baseline. The next
successful build establishes a new one.

== Update report and library consumers

[cols="2,2,3",options="header"]
|===
| Previous API | 0.7.0 API | Meaning
| Lock report format 1 `identity` | Format 2 `content_identity` | Provider-qualified pinned content, not a whole-build fingerprint.
| `LockSnapshot.source_identity` | `LockSnapshot.source_content_identity` | Returns the provider-qualified `ContentIdentity` value.
| Build result schema 1 `recipe_identity` | Schema 2 `build_identity` | The fully prepared native build request.
| `lock-snapshot-v1.schema.json` | `lock-snapshot-v2.schema.json` | Validate the current public projection.
|===

The current reader does not alias old fields or accept old report versions.
Historical tools can retain their matching pinned older core bundle; producers
and consumers moving to 0.7.0 must update together. A content identity, build
identity, original-file/tree/output digest and result path answer different
questions. Compare opaque identities only together with their provider.

Spec major 3 introduces explicit ownership and executor declarations. Lock and
report formats carry their own versions; they are not determined by package
version 0.7.0. Check the relevant version before consuming data.

== Use the integrated build interface

Use `blueprint plan build NAME` for declared relationships and add `--prepare`
for an exact build identity. Use `blueprint explain build NAME [--prepare]` to
compare against the last successful local build. Both accept `--json`; scripts
need not reconstruct relationships from lock and SBOM reports.

A managed build can reuse a provider result without adopting newly published
release bytes. Downstream release policy remains explicit: compare exact
prepared identities in capable admission CI, bind reviewed evidence to selected
configuration/files and artifact digests, and verify that binding on consuming
machines. Do not claim that a whole-lock checksum describes only the selected
producer inputs, or infer equal output bytes merely from input comparison.
