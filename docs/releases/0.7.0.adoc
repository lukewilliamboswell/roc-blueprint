= roc-blueprint 0.7.0

Blueprint now carries the Roc compiler it needs inside each released binary.
The first command that reads `Blueprint.roc` installs that compiler from the
binary into Blueprint's store, instead of downloading it from GitHub. A fresh
machine can bootstrap the compiler even when GitHub is unavailable.

The new `blueprint compiler-version` command exposes the exact bundled Roc
release tag, so downstream projects can check that their automation compiler
pin matches Blueprint's.

== Use 0.7.0

[source,roc,snippet=unchecked]
----
app [config] { pf: platform "{platform-url}" }
----

Binaries are attached for x86_64 Linux, arm64 Linux, Apple Silicon macOS and
x86_64 Windows, with SHA-256 sums in `blueprint.sha256`. Use this release's
binary with its platform URL. The importable core package is `{core-url}`.
Existing 0.6 configurations and lock files remain supported.

== Compiler available on first use

Each binary embeds only its own system's complete compiler archive, including
the supporting files Roc needs to link programs. The archive adds roughly
69–73 MB to the binary. It is installed into the existing content-addressed
store, checked against its recorded SHA-256 before extraction, and reused on
later runs. A damaged cached archive is restored from the embedded copy.

An explicit compatible `ROC` override still takes precedence, followed by a
compatible `roc` on `PATH`. Project packages and tools can still require
network downloads. Nix is required for tools from Nix package sources and
for sandboxed builds.

== Check an automation compiler pin

[source,sh]
----
blueprint compiler-version
----

This release reports `nightly-2026-10-18-1df370f`, followed by a newline. The
output has no label or colour and always describes the bundled compiler,
regardless of `ROC` or `PATH`. The command works in any directory, offline,
without evaluating a project, installing Roc or writing a cache. Native smoke
tests check the reported tag against the actual bundled `roc version` on
each released system.

A CI check or commit hook can compare the installed automation compiler:

[source,sh]
----
test "$(roc-stable version)" = \
  "Roc compiler version $(blueprint compiler-version)"
----

Consumers can also compare a committed compiler pin against that tag before
installing tools. Keep pin updates explicit so automation scripts can be
tested before adopting a new Roc release.

A project that declares the matching nightly through `Recipes.roc_nightly`
can reuse the archive Blueprint installed in its store for `roc-stable`.
An independently installed compiler, including one supplied by Nix, uses its
own installation; matching the version alone does not share that executable.

== Read committed pins from external tools

`blueprint lock show --json [NAME...]` exposes the entries in `Blueprint.lock`
without evaluating `Blueprint.roc`, starting a provider, accessing the network
or creating cache state. Its documented JSON format 1 includes exact remote
Nix `fetchTree` attributes and per-entry content identities, so external
scripts can use the locked revision and `narHash` without parsing the lock's
internal representation or maintaining a second pin.

An entry's identity stays the same when an unrelated source, fetched program
or task changes. Relative local sources retain their tree identity and have
no portable `fetchTree` recipe. Fetched-program identities remain distinct
from unpacked-tree identities. See
xref:commands.adoc#inspect-committed-pins[Inspect committed pins]
for the output schema and compatibility rule.

== Reproducible build recipes

Sandboxed builds compile a standalone runner from pinned shared Roc source
and a fixed compiler. The derivation no longer includes the Blueprint executable or caller
namespace identities. Runtime namespace observations are passed separately
and still refuse execution when isolation cannot be verified.

`Files([...])` selects a build's project files and directory trees; unrelated
application edits do not change that recipe's input tree. Omit it for the
existing whole-project snapshot. `Files([])` selects an empty project tree.
Separate builds can share a recipe while declaring their own single output.

`SourceFile(name, url, sha256)` declares an unchanged upstream file using its
published SHA-256. A recipe receives that file through `Inputs`, without
unpacking an archive or translating its digest into a tree hash. Its pin
lives in `Blueprint.lock`, and its verified bytes are reused from the store.
See xref:builds.adoc#original-files-with-published-hashes[Original file sources].

`blueprint build NAME --rebuild` checks an existing output by rebuilding the
same derivation and failing when the bytes differ. `--json` reports versioned
provenance with the actual derivation, outputs and locked sources used by the
build. `BLUEPRINT_TOOLS` exposes full roots of declared packages, so recipes
can reach libraries and loaders as well as executables. See
xref:builds.adoc#check-reproducibility-and-record-provenance[Build checks and provenance].

The platform writes Spec format 2.8. Configurations that do not select new
features retain their existing meaning; older consumers reject unsupported
required features explicitly.

== Describe and reuse artifact composition

The public `core.Sbom` API combines resolved Lock identities with reviewed
artifact composition and emits SPDX 2.3 JSON. It distinguishes build tools
from contained code and records incomplete or unknown coverage explicitly.
Inspection runs offline without evaluating a project or starting a provider;
binding the inventory to the final file's SHA-256 is a separate operation.

Consumers can import an upstream SPDX graph after verifying its document
digest and namespace, and bind its described subject to the resolved
artifact's digest, version and target. Imported identities and dependency
relationships remain available for downstream analysis.

Release executables and Roc source bundles have their own `.spdx.json`
sidecars, checked against the complete pinned SPDX schema and the actual
artifact bytes. They include reviewed native and transitive inputs and
explicit coverage gaps. These documents describe composition; they do not
establish build provenance or a vulnerability verdict. See
xref:sbom.adoc#artifact-bound-software-bills-of-materials[Artifact-bound software bills of materials]
for the API, reporting tool and supported import profile.

== Native documentation builds

The website and PDF manual now use the shared native `roc-docs` renderer
from roc-automation `tools-0.1.0-rc.1`, with reviewed executable checksums.
Documentation and release jobs use the matching shared action revision and
retain the generated API reference, PDF download and documentation archive.
Rendering no longer starts a Docker container.

The illustration and architecture diagram have prepared PNG assets. The
manual keeps its explicit section anchors and uses narrower responsibility
tables so their full contents fit the PDF. The API reference link uses its
published absolute URL; publication does not depend on `--site-url` support.
