= Bind and verify the complete sidecar set

`blueprint-sbom bind INVENTORY SUBJECT CONTEXT ARTIFACT` writes all supported
standard representations beside the final artifact: `.spdx.json` (SPDX 3.0.1),
`.spdx-2.3.json` (SPDX 2.3), and `.cdx.json` (CycloneDX 1.7). Its
`.sbom-manifest.json` lists all three by format, file name, exact SHA-256 and
size. The writer and checker use the same format/name table. A separate
SPDX 2.3 generation step is unnecessary.

The manifest also identifies the final subject bytes, inventory bytes and
explicit generation context. These are different identities: a source archive
checksum is not the checksum of its extracted source files or a linked binary.
A successful binding does not establish that every component is present in the
binary, that upstream license conclusions are complete, or that a publisher's
signature is authentic.

== Produce and verify a release

Generate the final artifact first. Supply reviewed inventory, subject and
context files, then bind once:

[source,shell]
----
blueprint-sbom bind inventory.json subject.json context.json app.tar.zst
blueprint-sbom check --manifest app.tar.zst.sbom-manifest.json \
  --artifacts . --inventory inventory.json
----

Publish the manifest and every file it names together with the exact subject.
Download all advertised standard sidecars before running the same check on the
consumer side. Check the release asset inventory too: no local checker can
find a remote file that the consumer did not download, or infer that an
arbitrarily named document was advertised as another representation.

The default manifest check measures the listed files *and* every existing
conventional standard sidecar of that subject beside the manifest. An adjacent
`app.tar.zst.spdx-2.3.json` omitted from the manifest is an error, even when
SPDX 3 and CycloneDX are correctly listed and hashed. A listed file that is
missing, altered or different in size is also an error. Each listed document
must name the manifest's subject and version, hold its final SHA-256, match its
listed format, and agree with other representations on the package graph.
Supplying `--inventory` additionally checks both the exact inventory bytes and
the document's evidence against that inventory.

All requested documents and the manifest are rendered and validated before
writing. Existing destinations are checked before the first write, and each
write exclusively creates a new file. This prevents an ordinary collision in
a later format from leaving earlier sidecars behind. It does not promise an
atomic multi-file transaction across process crashes or concurrent writers;
use an isolated release staging directory and publish only the complete
verified set.

== Explicitly limited and historical manifests

A named output remains useful for exporting one representation:

[source,shell]
----
blueprint-sbom bind inventory.json subject.json context.json app.tar.zst \
  compatibility.spdx.json --spdx-2.3 --manifest compatibility.sbom-manifest.json
----

This manifest deliberately describes one output. If other conventional
representations of the same subject are present beside it, a default check
refuses the unlisted files. To verify the declared subset explicitly:

[source,shell]
----
blueprint-sbom check --manifest compatibility.sbom-manifest.json --listed-only \
  --artifacts . --inventory inventory.json
----

`--listed-only` verifies the subject and every declared sidecar, with the
inventory when supplied. Its success message says “declared sidecars only”. It
does not assert that all advertised representations were covered. The flag
requires `--manifest` and is appropriate when checking an immutable historical
manifest that omits a separately published companion. Record that limitation;
do not rewrite a historical manifest or silently claim the omitted companion
is bound. Regenerate the complete set for a new release after upgrading.

Manifests may contain a deliberate subset of formats, but a format or file
cannot occur twice. Duplicate JSON keys, duplicate observations and unsupported
format names fail instead of selecting one interpretation.

== Library and custom publisher integration

`core.Manifest.renderings` is the supported `{ format, suffix }` table;
`Manifest.outputs(artifact)` returns all conventional `(path, format)` outputs.
Build the manifest from the documents actually emitted, without maintaining
another hard-coded list in a publisher.

`Manifest.check(text, observed)` compares the exact observed sidecar set and
rejects an observation absent from the manifest. The observation must come from
the publisher's advertised asset set or the consumer's directory discovery,
not solely from iterating `manifest.sidecars`: constructing it only from the
claims being checked cannot detect an omission. `Manifest.check_listed` is the
explicit subset-verification operation. Both refuse duplicate observations.

The repository's filesystem helper
`SbomFiles.observe_sidecars!(manifest_path, manifest, listed_only)` measures
listed names and, when `listed_only` is false, existing conventional names.
It preserves missing-file diagnostics for `Manifest.check` and refuses present
unreadable or nonregular candidates. This is the shared boundary used by the
standalone CLI and repository release checker.

A UUID document namespace is supported alongside the existing revision-qualified
HTTPS namespace. UUID namespaces reduce repeated SPDX 3 identifier bytes;
revision remains an explicit nonempty manifest context field. Namespace choice
does not change the SHA-256 or size of any final subject or sidecar binding.
