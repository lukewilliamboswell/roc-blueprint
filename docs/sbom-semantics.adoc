= SBOM runtime evidence, compact identities and supplier imports

== Runtime scope is a claim

CycloneDX `required`, `optional` and `excluded` describe runtime availability.
They are not certainty levels. In particular, `optional` means a component is
not installed or otherwise accessible at runtime; it does not mean that a
producer has only a dependency-lock entry or has not determined whether code
ships. An omitted scope defaults to `required` for standard consumers.

Blueprint's `standard-evidence-v2` CycloneDX profile therefore separates two
views of one inventory:

* The standard component tree contains the subject's proved containment and
  runtime dependency closure (`required`), together with proved build, test
  and development dependency closures (`excluded`). A library reached by both
  runtime and build paths is `required`.
* A component whose runtime role is unresolved is recorded once in a
  `blueprint:unresolved-component` property. The value is the complete typed
  `Sbom.Component` record, with the same bounded metadata rules as inspection.
  Metadata's `blueprint:unresolved-count` makes the partition visible without
  decoding every record.
* All inventory edges remain in `blueprint:relationship` properties. Standard
  dependency edges and addressed compositions refer only to standard-visible
  components. If unresolved records exist and no addressed subject assembly
  assessment was supplied, an `unknown` assembly composition is emitted.

This is intentionally a sound partial runtime view for generic CycloneDX
consumers. Standard component counts can be smaller than the full SPDX
inventory. The absence of candidate evidence from that runtime view is not a
claim of complete composition. Blueprint reconstructs the full inventory,
including unresolved records and edges, and checks it against the original
inventory just as for both SPDX formats. Cross-format agreement is checked
with `Sidecar.same_graph`, not by comparing only top-level component counts.

Completeness must still be reviewed explicitly. Address `Coverage` to a
component (including `Subject`) and `assembly` or `dependencies`; state
`complete`, `incomplete`, `unknown`, `excluded` or `verified-empty` with its
reason and contact. Unaddressed legacy claims stay evidence and do not become
broad standard completeness assertions. A producer must not reclassify
resolution candidates as build inputs just to put them in the standard view.

The reader retains `standard-containment-v1` and the older flat profile with
those profiles' original scope validation. Newly generated v2 output is
explicitly marked so an older reader refuses an unfamiliar interpretation.
`optional` remains a valid standard value in externally supplied CycloneDX;
Blueprint does not emit it without an explicit runtime-availability fact.

The semantics above follow the
https://cyclonedx.org/docs/1.7/json/[CycloneDX 1.7 scope and composition definitions].
Formulation is not a generic unknown-component bucket: a manufacture or
workflow role needs its own evidence.

== Short document identity without changing package identity

Use `Sbom.document_namespace(inventory, subject, identity)` for a generated
namespace, where `identity` contains `revision`, `created`, `author` and
`generator`. It returns a deterministic UUID version 8 URN derived from the
SHA-256 of the complete inventory, delivered subject and generation identity.
The canonical subject SHA-256 is still written in the standard subject
fields; the UUID identifies a document, not the delivered bytes.

Changing any of these document facts changes the namespace. Repeating the
same facts produces the same namespace. Every standard rendering can use the
same namespace, while the context and evidence retain the explicit revision.
Caller-supplied HTTPS namespaces ending in `revision-N` remain supported;
existing published namespaces are not rewritten on input.

SPDX 3 repeats document namespaces in identifiers and reference lists. A
45-byte UUID URN avoids repeating a long asset URL, release path and source
revision thousands of times. Generated non-package node suffixes are also
short; inventory component IDs remain unchanged. Required SPDX nodes,
relationships and element lists are retained. An alternative JSON-LD context
with a custom `@base` is not emitted because the official SPDX 3.0.1 JSON
schema requires the fixed standard context IRI.

== Standard metadata has one source of truth

New SPDX wire comments contain only fields not otherwise represented by the
standard: the reviewed kind, inventory identity, origin, target and modification
notes (or the subject's target and final-digest meaning). A
`blueprint_metadata_format` marker identifies `standard-fields-v1`.
Copyright, attribution, package URL and source references are read from their
standard fields rather than duplicated inside an escaped JSON comment.

The reader normalizes this compact representation into the existing canonical
`Sbom.Package.comment`, so `Sbom.package_of`, inventory comparison and
cross-format graph comparison keep their existing public value shape. It
also reads old full comments and still rejects conflicts between those old
duplicate assertions and the standard fields.

A valid changed standard field is not intrinsically detectable as false by a
reader: the standard field is authoritative in the document. Compare with the
inspected inventory using `Sidecar.against_inventory`, and verify the exact
sidecar bytes against their binding manifest, to detect such substitutions.
Do not add redundant assertions merely to make the reader guess which copy
is correct.

== Supplier evidence across multiple imports

An imported component's `modified` field holds a `blueprint-import-v1`
provenance record. It names the direct supplier document's namespace, URL,
SHA-256 and component ID; preserves the original modification or foreign
prose note once; and records normalization notes from this import.

When that component is imported again, Blueprint keeps its original
modification note and records the new direct supplier reference. It does not
embed the supplier's entire JSON metadata or recursively copy previous
provenance records. The immutable direct document reference is the route to
earlier evidence. Old opaque prose is preserved rather than stripped using
text heuristics. No URI is fetched during pure inspection.

This prevents successive JSON escaping from multiplying the same metadata.
The component-ID length and existing per-component, document, depth and graph
bounds still apply. A six-hop regression carries quote- and backslash-heavy
original modification notes exactly once while preserving all standard
metadata, local graph nodes and relationships.
